# ihomy 文档索引

> 一页地图:每份文档一句话定位 + 谁该读。新成员/新会话从这里出发,不必通读全部。

## 新人阅读顺序

1. 根 `README.md` —— 项目是什么,30 秒
2. `docs/架构设计.md` —— 系统怎么组成、一个请求怎么走、关键机制为什么这样设计,约 30 分钟通读
3. `AGENTS.md` —— 项目规则与约定(命名/数据库/代码规范/性能/索引/部署),写代码前必读;AI 会话自动加载
4. `docs/踩坑速查.md` —— 动手改某处前 grep 对应小节(工具链/后端/前端/天文/媒体引擎/WE/部署),避开已踩过的坑
5. `docs/需求设计说明书.md` —— 只读你负责业务域的 §4 小节 + §6 数据库设计,其余按需
6. `docs/变更归档.md` —— 按需检索(1MB+,**先查 `docs/归档索引.md` 定位行号或反查文件**,不要通读),找历史实现/踩坑/live DB 迁移 SQL

环境搭建与开发账号见本地《新人上手指南》(不入 git,由维护者直接发给新成员)。

## 文档维护规矩

- 新的变更归档**追加到 `docs/变更归档.md` 末尾**,不写回 AGENTS.md(AGENTS.md 只留规则+导航,目标 ≤30KB / 硬上限 45KB;体积由 `doc-drift-check.sh` 守住)。
- **生成物禁止手改**:`docs/代码地图.md`(`gen-code-map.sh`)、`docs/归档索引.md`(`doc-index.sh`)、`docs/变更归档.md` 顶部目录块。改了代码/路由/实体或归档小节后重跑脚本,CI 的 `--check` 会发现漂移。
- **踩坑写 `docs/踩坑速查.md` 对应小节**(按「症状 → 真因 → 对策」),AGENTS.md 顶多留一句结论级规定;机制参数、取证方法、维护清单同理,别塞回 AGENTS.md。
- 功能需求变更**就地更新** `docs/需求设计说明书.md` 对应功能章节(§4 功能 / §6 数据库 / §7 接口 / §9 规划),按功能组织、不写时间/版本叙事;顶部「修订记录」表**已整体移出**(2026-10-14,只留一节索引),版本沿革与实现历史一律查 `docs/变更归档.md`。
- **计数口径唯一来源**:表数以 §6.2 清单(与 `schema.sql` 实测 `CREATE TABLE` 条数)为准;实体/Controller/Api/页面/路由数不再写进 AGENTS.md,一律现查 `docs/代码地图.md`(脚本生成,不会滞后)。改完表后顺手同步 `README.md`、本索引、`docs/部署指导-*.md` 的表数口径(`doc-drift-check.sh` 会校)。
- 本索引新增/删除文档时同步更新。
