# ihomy 日志问题分析方法

> 面向运维/业务人员,不需要编程经验。跟着流程走,大部分报错 5 分钟内可以定位原因。
> 开发规范请看 [日志规范](./日志规范.md)。

## 1. 先拿到 tid(追踪号)

tid 是 16 位字符串(如 `590f7b47a6e84cb8`),一次用户操作的所有日志都用同一个 tid 串联。获取途径:

| 途径 | 说明 |
|------|------|
| **报错提示** | 页面右下角/右上角报错气泡里 5xx 级错误自带 `[tid:xxx]`,直接复制 |
| **运维-操作日志** | 运维管理 → 操作日志 → TID 列,点击即跳详细日志 |
| **响应头** | 浏览器 DevTools → Network → 任意请求 → 响应头 `X-Trace-Id` |
| **用户口述时间** | 都没有时,在操作日志里按时间/操作人过滤,找到那次操作的 tid |

## 2. 用「详细日志」页检索

运维管理 → 详细日志 tab → 粘贴 tid → 查询(默认查当天,历史问题选对应用日期)。

结果按时间排序,每条标注来源:

| 来源标签 | 含义 | 看什么 |
|----------|------|--------|
| 访问(access) | 客户端调接口 | 谁调的、调了什么接口、入参、返回 code、耗时 |
| 服务端(server) | 内部流程 + SQL | 执行了哪些 SQL 及入参、ERROR 及完整堆栈 |
| 第三方(thirdparty) | 调外部服务 | 天气/百度网盘/必应等是否正常、耗时、失败原因 |

## 3. 分析流程(四步)

```
① 访问日志定请求 → ② 看 code 定性质 → ③ 服务端日志找原因 → ④ 第三方日志排除外因
```

**① 访问日志确认"发生了什么"**

```
POST /api/blog user=demo_owner#3 ip=192.168.1.5 status=200 code=0 cost=35ms req={"title":"..."}
```

- `user` 谁在操作,`POST /api/blog` 做了什么,`req=` 传了什么参数
- `status` HTTP 状态码,`code` 业务码(0=成功),`cost` 耗时(>3000ms 会标 WARN)

**② 按 code 分流**

| 现象 | 含义 | 下一步 |
|------|------|--------|
| code=0 但页面不对 | 后端成功,疑似前端问题 | 看响应内容 resp=,再查前端 |
| code=5 / 400 参数类 | 入参校验没过 | 看 req= 里缺了什么/格式错在哪,基本是使用方式问题 |
| code=401 | 登录过期或未登录 | 正常现象,重新登录;批量出现查 token 服务 |
| code=500 | 后端异常 | **看服务端 ERROR 堆栈(第③步)** |
| 慢(WARN + cost 很大) | 性能问题 | 看该 tid 下 SQL 条数与第三方耗时,谁慢谁嫌疑 |

**③ 服务端日志找根因**

- 找 `ERROR` 级条目(红色标签),消息里就是完整堆栈:
  - 第一行 `xxx.YyyException: 具体原因` 是异常类型和消息
  - `at com.ihomy.开头的第一行` 是出错的应用代码位置(如 `com.ihomy.service.BlogService.create(BlogService.java:142)`),把它报给开发即可
- 看 SQL 条目(`==> Preparing` 语句 + `==> Parameters` 入参):
  - 参数对不对?(比如 familyId 是不是预期的)
  - 语句执行了没有?(只有 Preparing 没有 Parameters = 语句本身出错)
  - 同一条 SQL 出现异常多次 = 可能在循环里重复查询

**④ 第三方日志排除外因**

功能涉及外部服务时(天气、百度网盘、每日一图):看该 tid 下的 thirdparty 条目,`!!!` 开头 = 调用失败(有原因),`status=4xx/5xx` = 对方拒绝,`costMs` 特别大 = 对方慢。第三方失败但页面还能用 = 系统已降级,属已知行为。

## 4. 案例:用户说"我保存博客失败了"

1. 操作日志按时间找到那次"创建博客"记录,复制 TID:`bcb5b8ba4f0f4857`
2. 详细日志检索,访问日志显示:`POST /api/blog ... status=200 code=5`(WARN)
3. code=5 = 参数校验失败,看 `req=`:`{"title":"日志测试"}` —— 缺 content 字段
4. 结论:用户没填内容就点了保存,引导填完再保存。结束。

若是 code=500:找到服务端 ERROR 条目,把堆栈里 `com.ihomy.` 第一行 + tid 发给开发。

## 5. 伪终端排查(服务器上)

```bash
# 按 tid 捞全部三类日志(生产日志目录 /opt/ihomy/logs)
grep "tid:590f7b47a6e84cb8" /opt/ihomy/logs/access/*.log
grep "tid:590f7b47a6e84cb8" /opt/ihomy/logs/server/*.log
grep "tid:590f7b47a6e84cb8" /opt/ihomy/logs/thirdparty/*.log

# 只看错误
grep " ERROR " /opt/ihomy/logs/server/ihomy-server.log | tail -50

# 实时跟踪
tail -f /opt/ihomy/logs/server/ihomy-server.log

# 捞问题请求(access 里失败/慢的请求自动是 WARN)
grep " WARN " /opt/ihomy/logs/access/ihomy-access.log | tail -50

# 捞特定接口
grep "POST /api/blog " /opt/ihomy/logs/access/ihomy-access.log
```

Windows 开发机(PowerShell):

```powershell
Select-String -Path 'D:\WorkSpace\ihomy\logs\server\ihomy-server.log' -Pattern 'tid:590f7b47a6e84cb8'
Select-String -Path 'D:\WorkSpace\ihomy\logs\server\ihomy-server.log' -Pattern ' ERROR ' | Select-Object -Last 50
```

注意:终端里中文显示乱码(`?` 或方块)是终端编码问题,不影响日志文件本身(UTF-8 存储)。

## 6. 常见问题速查

| 现象 | 大概率原因 | 证据位置 |
|------|-----------|---------|
| 用户被登出 | access token 2h 过期后刷新失败 | access 日志连续 401 + refresh 请求 code≠0 |
| 天气不显示 | 和风 API 失败/配额尽 | thirdparty 日志 `!!!` 或 weather 条目 status≠200;运维页天气 tab 配额 |
| 百度网盘相册打不开 | 百度 API 失败/token 过期 | thirdparty 日志 baidu 条目;MISSING/OFFLINE 状态点 |
| 页面很慢 | SQL 慢或三方慢 | access WARN cost 值大;该 tid 下 SQL/thirdparty 的耗时分布 |
| 上传失败 | 文件超限/磁盘满 | access req=(multipart len=...);运维页服务器状态看磁盘 |
| 间歇性 401/404 | 双实例/端口冲突 | access 日志同 tid 出现在不同时间窗异常跳变(见 AGENTS 部署注意事项) |
| 操作日志没记录 | 注解缺失或落库失败 | server 日志搜 "操作日志保存失败" |
