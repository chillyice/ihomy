# 交互打断类修复 跨会话实施计划

> **状态**：**未开工**（2026-11-06 立项，来源 V11.40 审计产出）。本文件是这批修复的排期、口径与验收**唯一来源**；需求 §9.6 只留一行登记 + 指向本文。
> **立项来源**：V11.40 修完「贷款记录明细翻页被每分钟刷新顶回第 1 页」后，用户要求「检查全量系统中，是否还有其他地方存在这样的问题」。全站排查结论：**同款 bug 仅此一处，已修**；另发现 4 处「会打断用户、但根因不同」的相邻隐患，本计划收这 4 处。
> **交接方式**：新会话先读 `AGENTS.md` → 本文 → 需求 §4.3.6 / §4.4.4 / §4.5.10 / §4.12.2，再按 §10 开工清单执行。**版本号不要照抄**，按开工时根目录 `VERSION` +1。
> **非目标**：不改后端任何接口与表结构；不动分页/筛选/选中态语义；不做聊天消息持久化未读、不做脑图冲突合并、不做日程深链以外的滚动定位；不重构 `LoanDetailTable`（V11.40 已修，保持现状）。

## 0. 一句话方案

四项各自独立、互不依赖：①聊天室按「是否贴近底部」决定要不要自动滚，远离底部时改为浮标「新消息 · N」；②日程深链定位在用户主动滚动（wheel / touchmove / 方向键）时立即停表，并且本次深链不再抢；③把「按天变化的时间基准」抽成 `composables/useDayTick.js`，到期日历与贷款记录共用，替代 `computed` 里的 `new Date()`；④脑图应用远端数据前拍视口快照、渲染完成后还原，布局没变就不调会 `view.reset()` 的 `setLayout`。

## 1. 背景与排查结论（V11.40）

### 1.1 同款 bug 的判定条件

V11.40 那个 bug 要同时满足两条才会发生：

1. 分页（或其它局部 UI 状态）在**子组件**里；
2. 子组件用 **`watch(() => props.view)` 监听对象身份**，而父组件会周期性重建这个对象。

父组件 `LoanRecords.vue` 每分钟 `now.value = new Date()` → `cardViews` 重算 → `current` 换新对象 → 子组件 watch 命中 → `page.value = 1`。

## 2. 通用约束（四条都适用）

1. **不要再用「对象身份」当 watch 依赖**。需要「某类变化才重置」时，监听稳定键（业务 id、日期字符串、条数），不要监听 `new Date()` / 新对象。
2. **只夹取，不归零**。刷新后索引/页码越界就 `Math.min(max, …)`，不要回 0/1。
3. **定时器必须可停**：`onBeforeUnmount` 清 interval / timeout / 事件监听，一个都不能漏。
4. **不新增裸 `z-index`**：浮标用 `main.css` 的 `--z-action`（120）。不写 ≥100 的裸值（守门 `styles/zLayers.spec.js`）。
5. **所有可见文本走 `$t()`**：中英键结构对齐；新增键要同时进 `i18n/zh-CN.js` 与 `i18n/en.js`。
6. **含中文的源码必须用 Read/Write/Edit 改**，不要走 PowerShell 管道。

## 3. P1｜聊天室：翻历史时不被新消息拉回底部

### 3.1 现状与根因

`frontend/src/views/chat/Chat.vue`：

- `pushMsg`（120-124）追加消息后无条件调 `scrollBottom()`；
- `scrollBottom`（126-130）在 rAF 里 `scrollTop = scrollHeight`；
- 触发源是 WS `onmessage`（101-113），自己发的消息也走服务端广播回显。

用户在往上翻历史（距底 > 一屏）时，任何一条新消息都会把他弹回底部，阅读位置直接丢失。消息只保留最近 200 条（122 行截断），翻历史是正常使用路径。

### 3.2 修法

1. 常量与状态：
   ```js
   const NEAR_BOTTOM_PX = 80
   const unreadNew = ref(0)
   ```
2. 判定函数（必须在插入新消息**之前**调用，插入后高度已变）：
   ```js
   const isNearBottom = () => {
     const el = msgBox.value
     if (!el) return true
     return el.scrollHeight - el.scrollTop - el.clientHeight <= NEAR_BOTTOM_PX
   }
   ```
3. `pushMsg(m, { force = false } = {})`：
   ```js
   const wasNear = isNearBottom()
   messages.value.push(m)
   if (messages.value.length > 200) messages.value.splice(0, messages.value.length - 200)
   if (force || wasNear) scrollBottom({ clearUnread: true })
   else unreadNew.value += 1
   ```
4. `onmessage` 里传 `force`：`pushMsg(pkt.data, { force: pkt.data.senderId === myId.value })` —— 自己发的消息永远回到底部。
5. `scrollBottom({ clearUnread = false } = {})`：滚完后若 `clearUnread` 则 `unreadNew.value = 0`。
6. 模板：`.chat-box` 加 `position: relative`；消息区下方（输入区上方）放一个原生按钮：
   ```html
   <button v-if="unreadNew > 0" type="button" class="msg-jump" @click="scrollBottom({ clearUnread: true })">
     {{ $t('chat.newMessages', { n: unreadNew }) }}
   </button>
   ```
   样式：`position: absolute; left: 50%; transform: translateX(-50%); bottom: 72px; z-index: var(--z-action)`，半透明主题色、圆角 999px、`box-shadow` 用主题变量。
7. 用户在底部自己滚回时也要清浮标：给 `.msg-list` 挂 `@scroll="onMsgScroll"`，`onMsgScroll` 里 `if (isNearBottom()) unreadNew.value = 0`。滚动回调只做一次布尔判断，不加节流也可以。
8. `loadHistory()`（139-151）仍无条件 `scrollBottom({ clearUnread: true })`（首次进入定位最新）。

### 3.3 边界

- 只处理「追加消息」，不处理消息截断导致的位移。截断时若用户在上方，`scrollHeight` 变小会跳一下 —— 这是既有行为，**列为可选增强，本次不做**。
- 不做未读持久化、不做浏览器通知、不做 @提醒。
- 移动端软键盘弹起会改变 `clientHeight`；此时 `isNearBottom()` 返回 false 属于可接受误差（用户正在输入，本来就不该被抢滚）。

### 3.4 验收

| # | 操作 | 期望 |
|---|---|---|
| A | 往上翻超过 80px，另一账号发消息 | 不被拉底；出现「新消息 · 1」，再来一条变 2 |
| B | 点浮标 | 滚到底部、浮标消失 |
| C | 停在底部（距底 ≤80px）收消息 | 自动滚到底，不出现浮标 |
| D | 自己发消息（无论在哪个位置） | 一定滚到底 |
| E | 首次进入聊天室 | 定位最新，无浮标 |
| F | 翻到上方后手动滚回底部 | 浮标自动消失 |

### 3.5 风险

- `isNearBottom()` 放错时机（放在 `nextTick` 之后）会永远返回 false，浮标再也不出。**先算再 push**。
- 用 `behavior: 'smooth'` 会与 `TransitionGroup` 的 0.26s 动画打架，保持 `scrollTop` 直赋。
- i18n 新键 `chat.newMessages` 的中文建议「新消息 · {n}」，英文「{n} new messages」；不要用复数占位符（项目 i18n 没配 plural 规则）。

## 4. P2｜日程深链：用户一滚就停表

### 4.1 现状与根因

`frontend/src/views/schedule/Schedule.vue`：

- `scrollToFocus`（430-471）在 4 秒窗口内每 250ms 校正一次（最多 24 tick）——这是为了对抗「数据分批到、外壳挂载后把内容区滚回顶部、布局仍在变高变矮」，本身是合理的；
- 触发点：`watch([() => view.value, () => listGroups.value], … )`（490-496）与 `onMounted`（501）。`listGroups` 每次变化都会**重新起表**；
- 期间用户用滚轮/触摸主动滚走，下一 tick 又按绝对坐标拉回，表现为「页面自己动、用户抢不过」。

### 4.2 修法

1. 新增「本次深链是否被用户打断」标志：
   ```js
   let focusAborted = false
   ```
2. `scrollToFocus()` 开头：`if (focusAborted) return`。
3. 起表时按当前实际滚动容器挂一次性中断监听（`wheel`、`touchmove`、`keydown` 里只认 `ArrowUp/ArrowDown/PageUp/PageDown/Home/End/Space`），命中即 `focusAborted = true` 并 `stop()`。
4. `stop()` 里必须解绑这些监听（和 `clearInterval` 一起），并保证 `onBeforeUnmount`（504 附近）也调一次解绑。
5. 重置时机**只**在两处：`applyQuery()` 里真正设置了新的 `focusId`（284 行）之后，以及用户点击其它深链入口时。**不要**放在 `scrollToFocus()` 开头 —— 否则 `listGroups` 一变又重新抢。
6. `scrollIntoView` 那条路径（`onPickUpcoming`，319-325）是用户点击触发的，一次性，不在本次改动范围。

### 4.3 边界

- 用 `wheel` / `touchmove` / 方向键判断意图，**不要用 `scroll` 事件** —— 自己的校正也会触发 `scroll`，会立刻自我中断。
- `touchmove` 比 `touchstart` 稳（轻点不算滚），但惯性滚动开始前一定已经发生过 `touchmove`，来得及。
- 深链可能在 `.gc-main`（暖居主题）或 `window`（光尘主题）里，监听要挂在实际容器上；容器在第一次 tick 才算得出来，允许「第一 tick 之后才挂监听」。
- 用户中断后，同一次深链不再抢；换一个 `focus` id（浏览器前进/后退、点另一条「查看」）重新允许。
- 定位正常完成（连续 3 次就位或 24 tick 用尽）时行为不变。

### 4.4 验收

| # | 操作 | 期望 |
|---|---|---|
| A | 打开 `/plan?tab=plan&focus=<id>` | 首屏滚到该行并居中 |
| B | 定位过程中滚轮上滑 | 立即停住，4 秒内不再被拉回 |
| C | 定位过程中触摸拖动 | 同上 |
| D | 定位过程中按 PageDown | 同上 |
| E | 定位完成后滚轮滚动 | 与现状一致（本来就不会再抢） |
| F | 换另一条计划深链 | 重新定位 |
| G | 暖居 / 光尘两套主题各验一次 | 都正常 |

### 4.5 风险

- 监听解绑遗漏会泄漏到页面之外；`stop()` 与 `onBeforeUnmount` 双保险。
- 若把「已中断」做成 `ref`，`listGroups` 变化时的 watch 仍会调用 `scrollToFocus()`，但函数第一行就 return，没有副作用 —— 可以接受。
- 别为了「停表」把校正窗口从 4s 缩短，那会回归「深链定位不准」的老问题。

## 5. P2｜到期日历：跨天要重算

### 5.1 现状与根因

`frontend/src/views/book/finance/FinanceCalendar.vue:33`：

```js
const items = computed(() => upcomingMaturities(props.list, new Date(), 90))
```

Vue 的 `computed` 只追踪响应式依赖。这里依赖只有 `props.list`，`new Date()` 不是响应式 —— 数据不变就永不重算。页面长开跨零点后，「未来 90 天」窗口与「剩余 N 天」全部停在打开页面的那一刻。

同一形态在 `LoanRecords.vue` 已经用 `now` + 跨天 tick 解决过（V11.40，105-121 行），但那段逻辑是页面内的私有实现，本次抽成公用。

### 5.2 修法

1. 新建 `frontend/src/composables/useDayTick.js`：

   ```js
   // 按天变化的「今天」基准:定时器每分钟跑,但只在跨天时替换 Date 引用。
   // 下游可能用对象身份做 watch(V11.40 的教训),所以绝不能每分钟 new Date()。
   import { onBeforeUnmount, ref } from 'vue'
   import { todayStr } from '@/utils/date'

   export function useDayTick(intervalMs = 60000) {
     const now = ref(new Date())
     const tick = () => {
       const t = new Date()
       if (todayStr(t) !== todayStr(now.value)) now.value = t
     }
     const timer = setInterval(tick, intervalMs)
     const onVisible = () => {
       if (!document.hidden) tick()
     }
     document.addEventListener('visibilitychange', onVisible)
     onBeforeUnmount(() => {
       clearInterval(timer)
       document.removeEventListener('visibilitychange', onVisible)
     })
     return { now, tick }
   }
   ```

2. `FinanceCalendar.vue` 改：

   ```js
   import { useDayTick } from '@/composables/useDayTick'
   const { now } = useDayTick()
   const items = computed(() => upcomingMaturities(props.list, now.value, 90))
   ```

3. `LoanRecords.vue` 改：删掉本地 `dayKey` / `tickNow` / `nowTimer` / `onVisibility`（105-121 行），换成：
   ```js
   import { useDayTick } from '@/composables/useDayTick'
   const { now } = useDayTick()
   ```
   对外行为不变（`now` 仍是 `Date` ref，跨天才换引用）。

### 5.3 边界

- 定时器粒度 60s，跨天最多延迟 1 分钟 —— 与 V11.40 口径一致，可接受。
- 切后台再回来由 `visibilitychange` 补一次，手机端不会停在旧日期。
- 组件被 KeepAlive 缓存时 `onBeforeUnmount` 不触发；本项目 KeepAlive 只包移动端三个 Tab，这两个页面不在其中，不额外处理。
- 时间口径统一用 `utils/date.js` 的 `todayStr`（本地时区、只到日），不要引入 `Date.now()` 差值判断。

### 5.4 验收

| # | 操作 | 期望 |
|---|---|---|
| A | 打开理财页，把系统时间改到 23:59 后跨过 00:00（或切后台再回） | 到期日历的「剩余天数」与窗口内条目重算 |
| B | 同一操作看贷款记录页 | 已还期数/进度按新的一天重算，不回归 V11.40 |
| C | 停在同一页面 10 分钟不跨天 | 不重建对象、不触发下游 watch（可用 Vue Devtools 或临时日志确认） |
| D | 离开页面 | 定时器与事件监听已清（无控制台报错、无持续 tick） |

### 5.5 风险

- **最大的坑**：把 `now` 写成每分钟 `now.value = new Date()` —— 那正是 V11.40 的根因，会重新打断下游分页/滚动。必须只在 `todayStr` 变化时替换。
- `useDayTick` 依赖组件生命周期（`onBeforeUnmount`），只能在 `setup` 里调用，不能拿到 store/util 里用。
- 现有 `utils/date.js` 无上行依赖，直接 import 安全。

## 6. P3｜脑图：远端更新不重置视口

### 6.1 现状与根因

`frontend/src/views/tools/MindMapEditor.vue`：

- `pollRemote`（1291-1308）20s 拉一次详情；`saveState` 是 `dirty` / `saving` 时跳过（守卫正确）；
- 有远端更新时调 `applyRemoteData(record)`（1268-1289）；
- 该函数里，若布局与当前不同会 `mm.setLayout(parsed.layout)`，而库的 `setLayout` 内部直接 `this.view.reset()`（`node_modules/simple-mind-map/index.js:436-447`）——把 `scale / x / y` 归零；
- 随后 `mm.setData(parsed.root)` 触发 `CLEAR_ACTIVE_NODE` + `reRender`（`index.js:466-476`），布局重排后视口内容位置也变了。

结果：用户只是缩放/平移到某处浏览（没编辑，`dirty` 守卫放行），别人一保存，视图跳回左上角/原始比例。

### 6.2 修法

1. `applyRemoteData(record, { preserveView = true } = {})`，并且改为 `async`。
2. 改动前拍快照：
   ```js
   let viewData = null
   if (preserveView) {
     try { viewData = mm.view.getTransformData() } catch { viewData = null }
   }
   ```
   （`frontend/node_modules/simple-mind-map/src/core/view/View.js:155`，返回 `{ transform, state: { scale, x, y, sx, sy } }`。）
3. 布局：**只在真的不同时**才调 `setLayout`：
   ```js
   if (parsed.layout && parsed.layout !== mm.getLayout() && layoutOptions.some((o) => o.value === parsed.layout)) {
     layout.value = parsed.layout
     mm.setLayout(parsed.layout)
   }
   ```
   布局没变就跳过，直接避开一次 `view.reset()`。
4. 数据与还原：
   ```js
   mm.setData(parsed.root)
   await waitRender()          // 已有工具,461-481,240ms 超时兜底
   if (viewData) {
     try { mm.view.setTransformData(viewData) } catch { /* 库版本差异,保持默认 */ }
   }
   applyCanvasTheme()
   ```
5. 调用方：`restoreSnapshot`（1247-1255）已是 `async`，直接 `await applyRemoteData(restored)`；409 路径（1148 附近）与 `pollRemote`（1301）要么 `await`，要么 `applyRemoteData(record).catch(() => {})`，不允许裸调用产生未捕获 rejection。

### 6.3 边界

- `setTransformData` 内部会 `limitMindMapInCanvas` 夹取，位置可能有几像素修正 —— 可接受。
- `waitRender` 等待的是 `node_tree_render_end`，超时 240ms；必须在其后还原，否则按旧尺寸夹取。
- `setData` 会清空 active 节点与撤销历史，这是库行为。用户 `dirty` 时轮询已被守卫，不会走到这里；只浏览时没有可丢的编辑。
- 首次打开（`load()` → `applyRemoteData`）时 `mm.view.getTransformData()` 还是初始值，还原等于不动，不影响库的默认定位。
- 不做冲突合并、不做「有远端更新」提示条。

### 6.4 验收

| # | 操作 | 期望 |
|---|---|---|
| A | 两个浏览器开同一脑图；A 只缩放/平移到某处；B 编辑保存 | A 的 20s 内数据更新，比例与位置基本不变 |
| B | A 有未保存修改时 B 保存 | A 不自动刷新（现有 `dirty` 守卫保持） |
| C | B 改了布局结构 | A 数据更新，视图不跳回 1.0/左上（内容位置可因重排变化） |
| D | 历史快照回滚 | 数据回滚，视图保持 |
| E | 保存冲突 409 → 覆盖 | 覆盖后视图保持 |
| F | 首次打开脑图 | 与改动前一致（不空白、不偏移） |

### 6.5 风险

- `applyRemoteData` 改 `async` 后，调用的时序变化可能让「覆盖后立刻保存」读到中间态；确认 409 分支是「先覆盖再退出」即可。
- `mm.getLayout()` 返回常量，与 `parsed.layout` 字符串可能大小写/别名不一致 —— 实现时先在 `layoutOptions` 里归一化再比较，别直接字符串比。
- 库升级可能改 `View` API；用 `try/catch` 兜底，失败时退回现状（跳视口），不阻断数据更新。
