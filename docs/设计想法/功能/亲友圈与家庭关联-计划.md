# 亲友圈(家庭关联)与跨家庭分享 跨会话实施计划

> **状态**:设计定稿,未开工(2026-11-13)。**版本号不预占**,开工时按 `VERSION` +1。
> **立项来源**:用户 2026-11-13 的产品意见(原文):「现在有我,我老婆,我爸妈,她爸妈,各自是一个小家庭,但是家庭之间还有互相联系的地方,比如我妈发了照片了,不仅想自己存在 ihomy 里,还想分享给我们家庭看,那么就得想办法去关联……但是还要保证每个家庭之间还要相互独立,新增内容默认的权限都是仅家庭内可见……不要因为多家庭导致父母觉得在相互疏远,也不能让老婆觉得没有隐私。」
> **交接方式**:新会话先读 `AGENTS.md` → 本文 → 需求 §4.2(家庭与成员)/§6.4(visibility),再按文末开工清单执行。每阶段收尾走 `/archive` 轻量收尾。
> **非目标(明确不做)**:家庭合并 / 父子家庭层级 / 共享成员名单与家谱 / 共享账本 / 保险箱与私密内容进圈 / 自动全量同步 / 跨家庭编辑删除他人内容 / 「求分享」类催更互动。

---

## 0. 一句话方案

新增**亲友圈**(circle)作为「分享受众容器」:**一个圈 = 若干彼此独立的家庭**;内容默认仍只在自家可见,发布时**逐条显式**选择「只给自家人 / 加上某个圈」,接收家庭只能看到被分享的那几条,永远看不到发送家庭的其他内容。隐私靠「默认关闭 + 单向分享 + 可撤回 + 可审计」,亲情靠「一次点击就能分享 + 接收方有 '被惦记' 的轻提示」。

## 2. 目标形态

### 2.1 双圈结构(方案核心)

默认拓扑是**「我们家 = 两个圈的交汇点」**,公婆圈与岳父母圈**互不相通**:

```
      我爸妈家(B)                    她爸妈家(C)
           \                             /
      [ 圈① 我们这一边 ]          [ 圈② 她这一边 ]
                 \                   /
                  \                 /
                   我们家(A: 我 + 老婆)
```

- 用户场景落地:妈在 B 家发照片 → 选「加上 圈①」→ A 家(我和老婆)看到;C 家看不到。
- 老婆的隐私来自结构本身:**她爸妈家的内容和她家的分享默认不流向公婆,反之亦然**。只有两边都主动建「两家一起」的圈才会打通(需要 3 个家庭都同意)。
- 同一家庭可同时在多个圈(上限建议 3),A 家发布时逐次选择发到哪个圈。

### 2.2 四条铁律

1. **入圈 ≠ 共享**:加入亲友圈只获得「可以被分享给 / 可以分享给」的能力,**不获得读取圈内任何家庭内容的权限**。
2. **默认仅本家庭**:新建内容 visibility 仍是 `FAMILY`;分享是发布时的显式动作,不做任何默认外发。
3. **单向、可撤回、可审计**:谁分享谁撤回;发送家庭可随时查看「本月分享出去 X 条到 Y 家」并一键收回;接收家庭只能读被分享的具体条目,没有任何目录浏览/搜索/统计能力。
4. **作者主权**:默认只能分享自己创建的内容;家庭共有内容(家庭相册等)由 `sys_family_info` 的家庭策略决定,OWNER 可整体关闭对外分享。

### 2.3 可见性判定口径(新增一档「被分享」)

不新增 `visibility` 枚举值,判定改为两部分:

| 判定 | 规则 |
|---|---|
| `canView(content)` | ① 自家:`visibility=FAMILY` 且 `family_id=当前家庭`;② 自己写的 PRIVATE;③ 全家 `PUBLIC`(游客也看);④ **被分享**:`content_audience` 中 `target_id=当前家庭`;⑤ 相册特例:所属相册被分享给我,则相册内 `visibility!=PRIVATE` 的照片可看 |
| `canInteract(content)` | 能看即可点赞/评论;跨家庭**永不**可编辑/删除/移动/改可见性 |
| `canShare(content)` | 作者本人 + 内容属于当前家庭;家庭策略为 `OWNER_ONLY` 时 OWNER 可分享任意本家庭内容;`OFF` 时全禁 |
| 游客 | 只读演示家庭 PUBLIC(顺带修 §1.3 的跨库 PUBLIC 缺陷) |
| 跨家庭写操作 | `edit/delete/move` 一律 404(不泄露存在性) |

列表查询统一走 `applyVisible(wrapper, contentType, viewer)` → `nested(w -> w.eq(family_id, current).or().exists(受众子查询))`,**不引入 UNION**,分页语义不变。

### 2.4 情感与隐私设计(文案级,和权限同等重要)

| 场景 | 设计 |
|---|---|
| 发布弹窗 | 标签叫**「给谁看」**,不做「可见范围/权限」。选项三句人话:「只给自家人」/「自家人 + 爸妈家」/「自家人 + 亲友圈·一家人」。**默认第一项**,选过之后按内容类型记住上次选择 |
| 首次入圈确认 | 必须由对方家庭的 OWNER 点确认,并原句展示:「加入后,你们可以互相把照片、日记分享给对方看;**别人家里的其他内容你仍然看不到**,随时可以退出。」——这句话同时消解「父母怕被疏远」和「配偶怕没隐私」 |
| 接收侧呈现 | 卡片角标「来自 爸妈家 · 妈妈」,点进去只有这一条 + 点赞评论按钮;不出现「你没有权限」类冷提示(不可见即不存在) |
| 被惦记的反馈 | 子女首页顶部一条轻提示「妈刚分享了 3 张照片」(不进通知轰炸);**反向不打扰**——自家内容绝不主动推给父母 |
| 隐私可视化 | 家庭设置「分享记录」卡:本月分享 X 次 / Y 张照片 → 目标家庭列表 + 逐条撤回 + 「全部收回」。给透明账本比给开关更能消解焦虑 |
| 称呼 | 圈内每对关系可设称呼(「我爸妈」「岳父岳母」),避免统一称呼尴尬;圈名示例「一家人」「我们仨 + 爸妈」 |
| 诚实文案 | 撤回提示写明「对方将无法再打开,但已经保存到手机的图片无法收回」 |

### 2.5 明确排除

保险箱(`family_vault_item`)、账本、私密相册、`PRIVATE` 内容**永不进圈**;分享时若选中 `PRIVATE` 内容,前端直接不显示分享入口。

## 3. 数据模型(3 张新表,95 → 98)

```
family_circle            亲友圈(发起家庭 = 圈管理员)
family_circle_member     圈内家庭(含圈内称呼 alias)
content_audience         内容 → 接收家庭(圈在分享时展开为逐家庭行)
```

### 3.1 `family_circle`

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `name VARCHAR(50)` | 圈名,如「一家人」 |
| `cover_image VARCHAR(500)` | 可选 |
| `owner_family_id BIGINT` | 发起家庭(可改圈名/邀请/移除/解散) |
| `invite_code VARCHAR(16)` | 邀请码,可空 |
| `invite_expires_at DATETIME` | 默认 7 天 |
| `max_families INT DEFAULT 6` | 上限(含发起家庭) |
| `status VARCHAR(20)` | `ACTIVE` / `CLOSED` |
| `created_by`, `created_at`, `updated_at`, `deleted` | 常规 |
| 索引 | `uk_invite_code(invite_code)`、`idx_owner(owner_family_id)` |

### 3.2 `family_circle_member`

| 列 | 说明 |
|---|---|
| `circle_id`, `family_id` | 唯一键 `uk_circle_family(circle_id, family_id)` |
| `alias VARCHAR(30)` | 圈内称呼(「我爸妈」),仅本圈可见 |
| `invited_by_family_id` | 谁邀请的 |
| `joined_at`, `status` | `ACTIVE` / `LEFT` |
| 索引 | `idx_family(family_id)`(查「我当前家庭在哪些圈」) |

### 3.3 `content_audience`(分享受众,不用 `content_visibility`)

| 列 | 说明 |
|---|---|
| `content_type VARCHAR(20)` | `photo/album/video/blog/diary/wish/book` |
| `content_id BIGINT` | 内容 id |
| `owner_family_id BIGINT NOT NULL` | 内容所属家庭(校验 + 缓存失效用) |
| `target_type VARCHAR(20)` | 仅 `FAMILY`(圈在写入时已展开) |
| `target_id BIGINT` | 接收家庭 id |
| `source_circle_id BIGINT NULL` | 由哪个圈展开;退出/解散圈时按它批量收回 |
| `granted_by BIGINT` | 分享人 |
| `created_at` | |
| 唯一键 | `uk_audience(content_type, content_id, target_type, target_id)` |
| 索引 | `idx_target(target_type, target_id, content_type, content_id)`(列表命中)、`idx_content(content_type, content_id)`、`idx_circle(source_circle_id)` |

**为什么展开成 per-family 行、而不是存 `target_type=CIRCLE`**:列表查询只命中 `target_id IN (当前家庭)` 一个等值条件,索引最简;圈成员变更好收回(按 `source_circle_id` 批量删);「新家庭中途入圈看不到历史分享」天然成立。

**为什么不复用 `content_visibility`**:该表语义是「家庭内指定成员/群组」且无家庭维度字段,复用会让两套语义互相污染;保持它是预留死表不动。

### 3.4 `sys_family_info` 新增两列

| 列 | 取值 | 说明 |
|---|---|---|
| `circle_enabled TINYINT DEFAULT 1` | 0/1 | 0 = 本家庭完全不参与任何圈(加入也不生效) |
| `share_policy VARCHAR(20) DEFAULT 'SELF_ONLY'` | `SELF_ONLY` / `OWNER_ONLY` / `OFF` | 默认只能分享自己创建的;`OWNER_ONLY` = 家长可分享家庭共有内容;`OFF` = 禁止一切外分享 |

## 4. 判定与接口设计

### 4.1 新增 `service/access/`(阶段 A)

```
service/access/ViewerScope.java        请求期上下文:userId / isOps / currentFamilyId / isGuest
service/access/ContentAccessService.java
    applyVisible(wrapper, contentType, viewer)   // 列表过滤(单点)
    canView(contentType, content, viewer)        // 详情/点赞/评论
    canShare(contentType, content, viewer)       // 分享入口
    assertViewable(...)                          // 失败抛 NOT_FOUND
    familyMemberIds(familyId)                    // 通知用,查 sys_user_role 而非 sys_user.family_id
```

- `ViewerScope` 每请求构造一次(Controller/Service 参数显式传递,不用 ThreadLocal,便于单测)。
- 7 个内容 Service 全部改为调用它;`BlogMapper.xml`/`PhotoMapper.xml` 的两处手写过滤同步改由 XML 传参(或挪回 Service),**注释里「必须与 Service 手工对齐」的耦合点消灭**。
- 顺带修复 §1.3 三处既有缺陷(视频不过滤、游客跨库 PUBLIC、通知无校验)。

### 4.2 关键 SQL 形态

```sql
-- 列表:本家 OR 被分享(单表查询,分页语义不变)
AND ( p.family_id = #{familyId}
      OR EXISTS (SELECT 1 FROM content_audience ca
                  WHERE ca.content_type = 'photo' AND ca.content_id = p.id
                    AND ca.target_type = 'FAMILY' AND ca.target_id = #{familyId}) )
```

### 4.3 接口清单(登记进需求 §7.4)

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/circle` | `family:manage` | 建圈(当前家庭自动入圈) |
| GET | `/circle/list` | 登录 | 当前家庭所在圈 + 圈内家庭概要(家庭名/封面/圈内称呼,不暴露成员名单) |
| POST | `/circle/{id}/invite` | `family:manage` | 生成邀请码/邀请链接 |
| POST | `/circle/join` | 登录 | 凭邀请码加入(`{code}`) |
| PUT | `/circle/{id}` | `family:manage` | 圈名/封面 |
| PUT | `/circle/{id}/alias` | 登录 | 本家庭的圈内称呼 |
| DELETE | `/circle/{id}/family/{familyId}` | `family:manage` | 移除家庭(仅发起家庭) |
| POST | `/circle/{id}/leave` | `family:manage` | 本家庭退出 |
| DELETE | `/circle/{id}` | `family:manage` | 解散(仅发起家庭),`status=CLOSED` + 收回全部受众行 |
| GET | `/family/share-audit?page=` | 登录(本家庭) | 本家庭分享出去的条目(审计/撤回) |

### 4.4 缓存与通知

- 分享/撤回后:失效 `ihomy:home:pub:{ownerFamily}` **和** `ihomy:home:pub:{接收家庭}`(接收方首页会多一条)。
- 通知:分享时给接收家庭**全部成人成员**发 `SHARE_IN` 通知(`familyMemberIds` 查 `sys_user_role`,并校验接收者确实在该家庭);同类 10 分钟内聚合为一条。
- 跨家庭通知必须在写入前校验「接收者在目标家庭有角色」——顺带补 `NotificationService.create` 的缺口。

## 5. 阶段拆分

| 阶段 | 内容 | 依赖 | 可独立交付 |

## 12. 风险与取舍

| 风险 | 处置 |
|---|---|
| 可见性散落 7 处,直接加一档必漂移 | 阶段 A 先行,不加功能只收口 |
| 列表混入跨家庭内容后 N+1(作者名/家庭名) | 按 AGENTS 后端规范 7 批量 `selectBatchIds` + Map 回填 |
| 首页公开缓存按家庭,分享后另一家庭看不到 | 分享/撤回时对两个 familyId 都 evict |
| `PhotoMapper.selectLatestByFamily` 现不过滤 visibility,收口后可能「变少」 | 视为缺陷修复,单列变更说明,不混在功能提交里 |
| 一人多家庭 + 圈导致认知负担 | UI 只显示当前家庭的圈;切家庭后圈列表随当前家庭变化 |
| 邀请老人操作门槛 | 邀请链接(带圈码)点开即「XXX 邀请你加入亲友圈」,登录/注册后一键接受;不做二维码之外的额外步骤 |
| 撤回承诺过度 | 文案只承诺「无法再打开」 |
| 圈内家庭看到对方家庭成员名单 → 隐私外泄 | 接口只返回 家庭名/封面/称呼,不返回成员列表、成员数 |
