# 开源组件升级计划（2026-11）

> **状态**：**P0–P5 已完成并归档（V11.15、V11.16、V11.18、V11.19）**；只剩 Ruffle 0.7.1 与 Vite 8 产物的老 iPad 真机验收。本文是该批工作的**唯一排期与验收源**；需求 §9.1 只留一行指针。P3/P4/P5 的实施差异见 §7。
> **立项来源**：用户 2026-11-02「是否建议升级开源组件。如果是，制定升级计划。」
> **结论**：**建议升级，但必须分批、按风险推进，不建议一次性全量追最新。**
> **交接方式**：新会话先读根目录 `AGENTS.md` → 本文 → 需求 §4.6.10 / §9.1，再按文末「开工清单」逐批执行；每批完成按归档规则写四文档、跑闸门、bump `VERSION` 并打 tag。

## 0. 一句话结论

**先修「台账看不准」和「CI 跑在 EOL Node 上」这两件事，再按「后端补丁 → 前端运行时补丁 → 前端工程链（Vite 8）→ Vue 生态大版本 → 独立服务」五批升级。** 其中 Vite 8 是换内核（Rolldown/Oxc）的工程迁移，不是普通版本号 bump；MySQL 只走 8.4 LTS 补丁，不跟 26.x 创新版。

### 1.2 检测器缺陷（P0 必须先修，否则升级清单不可信）

1. **Maven 最新版取错源**：`backend/src/main/java/com/ihomy/service/OssComponentService.java:667-680` 用 `search.maven.org/solrsearch`，该索引已陈旧。实测 `spring-boot-starter-parent` 的 `latestVersion` 返回 **3.5.3**（索引时间 2025-06-20），而 `repo1.maven.org` 的 `maven-metadata.xml` 已到 **4.1.2**。后果：后端补丁长期不被台账发现。
2. **预发布版未过滤**：Spring Boot 的 `<release>` 当前是 `4.2.0-RC1`；`simple-mind-map` 的 npm `latest` 是 `0.14.0-fix.3`。`common/OssVersionUtil.java:52-68` 只比数字段，会把这些预发布当成正式升级项。
3. **SERVICE 版本轨道未区分**：MySQL 的 GitHub latest 是 `mysql-cluster-26.7.0`（创新版），不是本仓在用的 8.4 LTS；Jellyfin 台账显示 `v12.2`，但当前开发网络访问 `api.github.com` 超时（curl 返回 000），**无法核实**。
4. 已有兜底仍有效：`OssComponentService.java:601-612` 在列表/汇总时按「current vs latest」重算，`latest` 不高于 `current` 的不会算升级项。所以库里残留的 `MyBatis-Plus 3.5.7`、`Spring Boot 3.5.3` 等低版本不会真的把用户带去降版，但检测结论本身是错的。

### 1.3 工具链事实（决定批次顺序）

- **Node 20 已 EOL**（2026-04-30）。本机实际 **v24.18.1**，但 `.github/workflows/ci.yml:39` 仍是 `node-version: '20'`，`AGENTS.md:239` 也还写 Node 20。
- **Vitest 5** 要求 Node `^22.12 || ^24 || >=26`；**vue-i18n 11** 要求 Node `>=22`；**pdfjs-dist 6.5** 的构建 engines 为 `>=22.13`。因此 Node 基线必须从 20 抬到 **24 LTS**（22 也在支持期，但本机已是 24，统一到 24 更省事）。
- **Vite 8 换成 Rolldown + Oxc**：`build.rollupOptions` 更名 `build.rolldownOptions`；**对象形式的 `output.manualChunks` 不再支持**，要改 `advancedChunks.groups`（或 `codeSplitting`）；默认浏览器目标升到 Chrome 111 / Safari 16.4；CSS 压缩默认 Lightning CSS。本仓 `frontend/vite.config.js:77-90` 正好用的是对象式 `manualChunks`。
- **浏览器目标已定（2026-11-02）**：家里有 iOS <16.4 的设备，不能接受 Vite 8 的默认目标。P3 必须显式设 `build.target` 与 `build.cssTarget` 回到 Vite 5 的 `modules` 下限（Safari 14 / Chrome 87 / Edge 88 / Firefox 78），并在最老的 iPad 上实测；若该设备低于 iOS 14，按实际版本再降一档并记录。
- **Vitest 5** 的 `clearMocks` 默认改为 `true`；配置文件中不再向父目录查找；`vi.mock` 等必须在顶层。
- **Vue Router 5 / Pinia 4** 的 peer 已对齐 Vue 3.5.x；Router 5 对 Vite 7/8、Pinia 3/4 是**可选 peer**，但说明这几个大版本属于同一生态波次，应放在 Vite 8 之后。

## 2. 目标与非目标

**目标**

1. 消除 EOL 运行时风险：CI 与本机统一到 Node 24 LTS，`engines` 写进 `package.json`。
2. 让台账「可信」：Maven 检测改用 `repo1.maven.org` 元数据、过滤预发布、区分 SERVICE 版本轨道。
3. 后端补丁到位：Spring Boot 4.1.2 + MyBatis-Plus/SpringDoc/Hutool/JJWT/Lombok 补丁。
4. 前端运行时保持小步快跑：Vue/Element Plus/axios/marked/hls/pdfjs/three 等 PATCH/MINOR 先落地。
5. 完成 Vite 8（Rolldown）迁移，重设并记录入口 chunk 基线。
6. 完成 Vue Router 5 / Pinia 4 / vue-i18n 11 大版本升级。
7. 独立服务只做安全的补丁级更新。

**非目标**

- 不做 CVE/漏洞扫描（2026-09-29 已决策不做，台账三列保持预留）。
- 不追 MySQL 26.x 创新版、MySQL Connector/J 26.x。
- 不把 Renovate 自动 PR 当作前置条件；手工升级步骤即闭环，`autoUpgrade.available` 只是可选路径。
- 不引入任何新依赖，不改业务功能、表结构、接口契约。
- **不做 MySQL 9.7 LTS 迁移**（2026-11-02 已明确不升级）；MySQL 只维护 8.4 LTS 补丁线。

## 3. 分批计划

> 每批独立分支、独立提交、独立验收；不要在同一工作树并行跑 `npm run build`（会争 `public/emulatorjs` 与 `dist/`）。版本号按归档时的 `VERSION` 顺延，本文不预占。

### P0 — 闸门修复（约 0.5 天）

**为什么先做**：不修检测器，后面每一批的「可升级项」都不可信；不抬 Node，前端工程链根本装不上。

1. **Maven 检测改源**
   - `OssComponentService.fetchMavenLatest` 改为拉 `https://repo1.maven.org/maven2/{group}/{artifact}/maven-metadata.xml`（`group` 的点换成路径）。
   - 选版规则（同时避开两个坑）：
     a. 先取 `<release>`；若它是稳定版（不含 `-RC`/`-M`/`-SNAPSHOT`/`-fix` 等字母后缀），**直接用它**——这能避开 MyBatis-Plus 仓库里 `3.5.18.1` 与 `<release>3.5.18</release>` 的歧义；
     b. 若 `<release>` 是预发布（如 Spring Boot 的 `4.2.0-RC1`），回退到 `<version>` 列表，过滤预发布后取最高稳定版（得到 `4.1.2`）；
     c. 两者都取不到则返回 null，保留上次检测结果。
2. **预发布过滤**
   - `OssVersionUtil` 增加「是否预发布」判断；`updateType` 对预发布目标返回 `NONE`（或检测阶段直接不写 `latest_version`）。
   - 补 spec：`0.14.0` vs `0.14.0-fix.3`、`4.1.1` vs `4.2.0-RC1`、`3.5.17` vs `3.5.18.1`。
3. **版本轨道降噪**
   - MySQL 行置 `status=IGNORED`，`purpose` 写明「跟踪 8.4 LTS，不跟 26.x 创新版」；MySQL Connector/J 行同样置 `IGNORED`（跟随 8.4 LTS 服务器，暂不采用 26.x 日历版本线）。
   - Jellyfin 行待联网核实后再定；不为此新增表列，先用既有 `status` 机制，避免扩大改动面。
4. **Node 基线**
   - `.github/workflows/ci.yml:39` → `node-version: '24'`。
   - `frontend/package.json` 增加 `"engines": { "node": ">=22.12" }`。
   - `AGENTS.md:239` 的「Node 20」改为「Node 24 LTS（最低 22.12）」；同步 `docs/新人上手指南.md`（如有版本表述）。
5. **台账计数修正**
   - `schema.sql:2142` 注释 55 → 57（31→33 NPM）。
   - 需求 §4.6.10「种子 53 项 / NPM 29」→「57 项 / NPM 33」，并补登 DOMPurify、js-yaml、fflate、yaml、smol-toml 的说明。

**验收**

- 新增/更新 `OssVersionUtil` spec 全绿；`mvnw -B test` 全绿。
- 重启后端后 `POST /ops/oss/check`，台账里 Spring Boot 行应显示 **4.1.2**、Hutool **5.8.48**、MyBatis-Plus **3.5.18**、SpringDoc **3.2.0**、Lombok **1.18.48**；JJWT 会显示 **0.13.0**（MINOR，P1 仍按计划只升到 0.12.7，此项保持可见、不点确认）。
- `simple-mind-map` 不再出现在可升级项；MySQL 服务与 Connector/J 已置 `IGNORED`，不再计入升级角标；Jellyfin 的 `v12.2` 若仍无法核实，保持原样并在汇报里注明。
- `bash scripts/doc-drift-check.sh` 全 `[OK]`。
