## 1. 项目概述

### 1.1 项目背景

为家庭成员之间的内容共享与互动记录提供服务,本项目构建家庭内部使用的内容平台,应用名 ihomy。系统支持电脑浏览器、安卓、iOS 三端访问,保证多设备的一致性,以 PWA 形式发布。

### 1.2 项目目标

- 一套代码覆盖 PC 浏览器、安卓、iOS 三端(设备体验一致,PWA 形式)
- 支持家庭角色(家长/成员/孩童/访客),权限分级管理
- 邀请码注册设计,首页模块化快速家庭接入
- 内容模块:博客、日记、相册、放映厅、聊天室、积分商城、任务悬赏、提醒、家庭计划、愿望单、记账、家谱等
- 首页模块化设计可扩展,新功能即插即用

### 1.3 术语表

| 术语 | 说明 |
|------|------|
| PWA | Progressive Web App,可安装到桌面 |
| JWT | JSON Web Token,无状态身份令牌 |
| OWNER/MEMBER/CHILD/GUEST | 家长/成员/孩童/访客 四级角色 |
| OPS | 运维管理员(不属任何家庭) |
| AOP | 面向切面编程,用于自动记录操作日志 |
| RBAC | 基于角色的访问控制(用户-角色-权限三层) |
| share_token | 家庭分享混淆 ID(16 位随机,替代数字 home_id) |

## 4. 功能模块清单(按业务域归档)

### 4.1 认证与账号

#### 4.1.1 注册与登录

- **Controller**: AuthController;**Service**: AuthService;**关键表**: sys_user / sys_user_role / sys_family_info
- 邮箱=账号(uk_email 唯一),大小写不敏感
- 注册必填:邮箱 + 密码 + 确认密码 + 图形验证码
- 注册可带邀请码加入家庭,或创建新家庭(新家庭默认私有 is_public=0;自动注入 9 个默认博客分类)
- 注册成功**不自动登录**,跳转登录页
- 登录请求体:`{email, password, captchaId, captchaCode}`
- **邀请码状态校验**:`status==INVITE_UNUSED` 才放行(曾误写 INVITE_USED)
- JWT 双 token:access 2h + refresh 7d(Redis 黑名单登出失效);claim 含 userId/username/role/familyId/permissions/isOps
- refresh 时按优先级解析当前家庭:Redis > default_family_id > family_id;续期时两个 token 都轮换(滑动续期)
- **HTTP 401 约定**:`authenticationEntryPoint` 必须返回真实 HTTP 401 状态码(JSON 体照写),前端 axios 只对 HTTP 401 触发 refresh 续期
- **演示(访客)账号**:`demo@ihomy.local` / `demo2@ihomy.local` / `demo3@ihomy.local`(演示家庭 OWNER/MEMBER/CHILD,仅存在于开发库);密码不入仓库,登录页预填由前端 `.env.development.local` 的 `VITE_DEMO_*` 提供(仅 vite dev 加载,生产构建不读取)

#### 4.1.2 图形验证码

- **Controller**: AuthController;**Service**: CaptchaService;**存储**: Redis captcha:{id}
- `GET /auth/captcha` 返回 {captchaId, image(base64)}
- 5 分钟 TTL,一次性校验(通过即删);错误/重用返回 1006
- 开发环境固定 `qwer`(`app.captcha-fixed-code`)
- 实现:Java2D 绘制 4 位字符 + 干扰线/噪点

#### 4.1.3 个人资料

## 6. 数据库设计

### 6.1 RBAC 权限模型

采用 RBAC(基于角色的访问控制),用户-角色-权限三层模型:

sys_user ──< sys_user_role >── sys_role ──< sys_role_auth >── sys_auth

- **sys_user**:用户表,不含角色字段(角色通过关联表绑定)
- **sys_role**:角色表,预设 OWNER/MEMBER/CHILD/GUEST + OPS
- **sys_auth**:权限表,定义具体权限点(如 blog:create、album:manage)
- **sys_user_role**:用户-角色关联,同一用户在不同家庭可有不同角色(含 family_id)
- **sys_role_auth**:角色-权限关联,定义某角色拥有哪些权限

### 6.3 命名规则

- **主键**:`id BIGINT PK`(MyBatis-Plus `@TableId(type=INPUT)`,手动赋值或雪花)
- **软删**:`deleted TINYINT`(MyBatis-Plus `@TableLogic`);**物理删必须自定义 XML DELETE**(MP deleteById 实为 UPDATE)
- **时间字段**:`created_at` / `updated_at`(DATETIME)
- **家庭隔离**:所有业务表带 `family_id`
- **枚举字段**:状态/类型一律大写英文单词(`PUBLISHED/DRAFT/PUBLIC/FAMILY/ACTIVE...`),含义存字典表 `sys_dict_item`,**不用数字**

#### 一、同义词表 + 录入自动联想别名

**目标**:解决「纸巾/卫生纸/厕纸/手纸」这类多词一义——用户录入时自动联想合理别名并写入可生长的同义词表,找物时读表扩展,任何叫法都能命中同一条物品。零 token、离线优先,LLM 负责联想扩充。

**1. 新增 `sys_synonym` 表(全局、可生长)**
```sql
CREATE TABLE `sys_synonym` (
  `id`         BIGINT      NOT NULL AUTO_INCREMENT COMMENT '主键',
  `canonical`  VARCHAR(50) NOT NULL COMMENT '规范词(如 纸巾)',
  `alias`      VARCHAR(50) NOT NULL COMMENT '同义别名(如 手纸)',
  `source`     VARCHAR(20) NOT NULL DEFAULT 'BUILTIN' COMMENT '来源:BUILTIN/LLM/USER',
  `created_at` DATETIME    DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_syn` (`canonical`, `alias`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='同义词表(全局可生长;录入联想+找物扩展共用)';
```
- 同时写 schema.sql 与 migrations.sql(V9.52 幂等段),并灌入 BUILTIN 种子(规范词 + 别名逐行 INSERT)。示例组(完整清单实现时定,宁缺毋滥):纸巾/卫生纸/厕纸/手纸/面巾纸、遥控器/遥控/遥控板、剪刀/剪子、充电器/充电头/充电线/数据线、洗发水/洗头膏/洗发液、拖鞋/凉拖/棉拖、毛巾/洗脸巾/面巾、水杯/杯子/口杯、电饭煲/电饭锅、吹风机/电吹风/风筒、垃圾桶/垃圾篓/纸篓、台灯/床头灯、袜子/短袜/长袜。
- **表数 63→64**:实现时同步 §6.2 表清单与 AGENTS.md 表数口径。

**2. 内存预热 + 写入 evict**
- 新增 `SynonymService`:启动 `@PostConstruct` 把全表读进内存 `Map<String,String>`(alias→canonical)与 `Map<String,List<String>>`(canonical→组内别名),懒加载兜底(参照 `sys_home_module` 的 `globalLoaded` 双检锁);`upsert(canonical, alias, source)` 写入后 evict。数据量小,不引第三方缓存。

**3. 找物读表扩展**
- `ItemLocalParser.findLocal`:先用 `SynonymService.expand(query)` 生成变体列表(原文 + 把 query 中命中的同义词替换为组内其它成员的变体,上限约 8),对每行取 `max(score(row, variant))`,其余打分/排序/limit 20 不变。
- `ItemAiService.llmFind`:关键词拆解后同样按同义词表扩展(可选,LLM 已自带别名的场景收益较小,可后做)。

**4. 录入自动联想别名(两条路径都补)**
- LOCAL(零 token):`ItemLocalParser.parsePut` 抽出物品名后查 `SynonymService` 归一化——命中则 name=规范词、aliases=组内其余成员逗号拼接,再 `guessType`(修正「手纸」不被 DAILY 识别的问题);`PutPlan` 带 aliases 传回 `executePut`(它已支持按名/别名命中后挪位更新,自动把「手纸」「卫生纸」归并到「纸巾」不新建重复)。
- LLM:增强 `ItemAiService.PUT_SYSTEM_PROMPT`——把当前同义词表规范词集合作为上下文传入,要求 LLM **优先复用已有规范词、输出 3~5 个常见同义叫法**;`executePut` 落库 `item.aliases` 的同时,把 LLM 新给的 (canonical, alias) 对 `SynonymService.upsert(..., source=LLM)`。这样后续任意家庭/物品都认识这个词。

**5.(可选二期)找物确认回写**:找物模糊命中时前端弹「你是不是在找:纸巾(也叫卫生纸/厕纸/手纸)?」,用户确认后把该叫法 `upsert(source=USER)`。覆盖内置词典外的家庭特有叫法。

#### 二、功能二级兜底模型(第一不足 → 第二补强)

**目标**:把 `ItemAiService.find/put` 里已写死的「本地优先 → LLM 兜底」抽象为每个功能可配置的「主模型 + 兜底模型」,并推广到全部 5 个功能。

**1. schema:功能绑定加兜底列**
```sql
ALTER TABLE `sys_family_ai_feature`
  ADD COLUMN `fallback_model_id` BIGINT DEFAULT NULL COMMENT '兜底/辅助模型 id(可空;主模型不足时启用)' AFTER `model_id`;
```
- 同步 schema.sql 与 migrations.sql(V9.52 幂等段)。

**2. 解析:`FamilyAiConfigService`**
- 保留 `resolveForFeature` 返回主模型;新增 `resolveChain(familyId, featureCode)` 返回 `record Chain(AiConfig primary, AiConfig fallback)`(兜底为空则 null)。
- 校验:兜底也必须落 `AiConst.FEATURE_ALLOWED_TYPES` 内;兜底 != 主模型。

**3. 执行:每功能独立的「不足」判定**
- 抽一个小工具或按项目风格在各功能 Service 显式写「try 主 → 判定不足 → try 兜底」。判定表:

| 功能 | 主模型 | 「不足」判定 | 兜底模型 |
|---|---|---|---|
| ITEM_FIND | LOCAL | 本地闭集无命中 | LLM |
| ITEM_PUT | LOCAL | 正则解析不出物品/位置 | LLM |
| ITEM_FIND/PUT | 便宜 LLM | matches 为空 / 解析不出 | 强 LLM |
| CHAT | LLM | 仅 报错/超时 | LLM(容灾) |
| IMAGE | IMAGE | 生成报错/被拒 | IMAGE(容灾) |
| ASR | ASR | 识别报错/空结果/低置信 | 另一 ASR(容灾+精度) |

- **要点**:找物/放物是「质量兜底」(结果为空才换);CHAT/IMAGE/ASR 基本是「容灾兜底」(报错才换)。CHAT 不要试图自动判定「答得不好」,否则每句话双倍烧 token。

**4. 设置页 + 绑定接口**
- 前端「家庭 AI 配置」面板 5 个功能各加第二个下拉「兜底模型/辅助模型」(可空、同类型过滤、不能和主模型重复);`getFeatures` 回传 `fallbackModelId/fallbackModelName/fallbackModelType`;`bindFeature` 增加可选 `fallbackModelId` 参数并校验;i18n 中英补「兜底模型」文案。

**5. 迁移(保持现行为无损)**
- 对 ITEM_FIND/ITEM_PUT 既有行:model_id 指向 LLM 的 → `fallback_model_id = model_id`,`model_id = 该家庭 LOCAL 模型 id`;model_id 指向 LOCAL 的 → 保持,兜底 null。其余功能兜底 null。
- 效果:找物/放物主=LOCAL、兜底=原 LLM,与当前「本地优先→LLM 兜底」行为完全一致。

**6. 文件改动清单**

| 文件 | 改动 |
|------|------|
| `resources/schema.sql` + `migrations.sql` | 加 fallback_model_id 列 + 迁移既有绑定 |
| `entity/AiFeature.java` | 加 fallbackModelId 字段 |

#### 四、概念澄清(学习背景:规则 / 机器学习 / 蒸馏)

> 本小节用于理解「为什么这样设计」,不涉及具体实现,可跳过不影响执行。

实现「智能」有两条并行路线:

1. **符号 AI / 规则系统**(传统):人写规则、查表、正则。确定性、可解释、零成本。
2. **机器学习**(从数据学出规律/参数):
   - 传统 ML(决策树/逻辑回归/SVM…):需人工特征工程 + 训练;
   - 深度学习(神经网络):自动学特征,需海量数据与算力,LLM 是这条路的巅峰。

本计划各部分的归属:

| 本计划内容 | 路线 | 是否机器学习 |
|---|---|---|
| 同义词表 + ItemLocalParser 本地规则 | 符号 AI(查表/正则) | 否(人写规则) |
| LLM 兜底(chatJson) | 深度学习产物 | 用深度学习,但不训练 |
| 功能兜底模型(第一不足→第二补强) | 工程路由/级联 | 否(调用逻辑) |

整体架构 = 「规则第一层 + 大模型兜底第二层」的混合(hybrid / 级联),本身不是机器学习,但第二层依赖机器学习造出的产物(LLM)。

**与「学习蒸馏」的区别**:蒸馏是训练技术——用大模型(teacher)的软标签训练小模型(student),产出新权重、逼近 teacher 的通用能力;本计划做的是「结果固化(把 LLM 输出存成符号数据) + 推理路由」,不训练任何模型。方向上两者都算「越用越聪明」,但蒸馏改模型,本计划改数据与调用逻辑。

**何时才真正「做」机器学习**(在本领域):
- 方案三 embedding 语义匹配(用预训练模型做向量相似度检索;通常仍属「调用」而非「训练」);
- 无监督聚类:从家庭历史叫法自动聚出同义组(免人工列种子);
- 学习蒸馏 / 个性化排序(按点击历史学偏好)。

上述均需训练数据 + 算力,而 ihomy 生产为 2GB VPS / `-Xmx384m`,「纸巾=卫生纸」一张表零成本即解决,训练模型来记它属杀鸡用牛刀。**结论:本计划「用」ML 成果(LLM)而非「做」ML。**

> 优先级含义:P1 用户价值高且技术上可行(依赖最少);P2 锦上添花;P3 结构性改动;P4 依赖外部条件(短信商/商业决策)。实现新功能前先 `grep schema.sql + router/` 对照模块种子。
