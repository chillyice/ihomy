# 数据备份与迁移

> 站内备份(V14.51 起):运维页统一管理**备份策略**(每条策略自己选模块、周期、清理与启停),家庭设置页由家长导出自家数据。
> 恢复一律在服务器上按包内 `RESTORE.md` 执行,**站内不做全库覆盖恢复**(避免误点把线上数据清空)。
> 功能口径见 `docs/需求设计说明书.md` §4.6.12,接口见 §7.5。

## 1. 备份策略与模块

一条策略 = 名称 + 勾选的模块 + 执行周期(每天 / 每周 / 每月 + 时间 + 星期几或几号)+ 可选保留天数 + 启停。可以新建多条,例如「每天全量 03:30 留 7 天」+「每周一基础数据 05:00 留 30 天」。

模块与表是**显式映射**(`service/backup/BackupModule`),不按前缀猜;新增表必须归入某个模块,`BackupModuleCoverageTest` 会拿 `schema.sql` 校验漏表:

| 模块码 | 覆盖内容 |
|--------|---------|
| MEMBER | 家庭、成员、角色权限、邀请、通知等账号域 |
| LIFE | 家庭事务:物品、账本、贷款、保险箱、家谱、相册索引等 |
| SCHEDULE | 日程、提醒、纪念日、计划、节假日 |
| BOOK | 记账、贷款、预算等家庭账本表 |
| CONTENT | 博客/日记/照片/视频/图书/心愿等 `content_*` |
| CHAT | 聊天室与私聊消息 |
| HEALTH | 健康数据与上报令牌 |
| GAME | `game_*` 小游戏记录 |
| REPORT | `report_*` 报表与日志 |
| CONFIG | 系统参数、字典、首页模块、AI 模型池、备份策略自身等配置 |
| FILES | **不对应表**,勾选后额外打包 uploads 全部文件(硬链接增量) |

- 不勾 `FILES` 只导库,体积小、速度快;勾了才会把照片/视频/图书等实体文件一起打进包。
- 每张表只能归一个模块,`BackupModule` 是唯一事实来源;`sys_backup_job` 与一次性令牌 `sys_password_reset_token` **永不进备份**。
- 文件未变化时用**硬链接**指向上一份真正带文件的备份,只有新增/改动的文件才真正落盘,所以抓的是「实际磁盘占用」与「逻辑体积」两套数字。

一条策略默认每天 03:30 全模块 + 上传文件、保留 7 天(由 `schema.sql` / `migrations.sql` 种一条「每日全量备份」)。

### 保留与清理

- 每条策略按自己的**保留天数**清理,留空 = 不自动清理;**最新一份永远保留**(即使已超期)。
- 清理跑两个时机:每个备份任务成功之后 + 每天 05:00 定时;只删文件,记录转 `PURGED` 留审计。
- 删除策略只停定时,历史任务与备份文件仍按原保留规则处理;之后这些任务按 **30 天**兜底清理。
- 旧版固定类型任务(`policy_id IS NULL`,升级前产生的)沿用 GFS 三代:基础/内容 7 日 + 4 周 + 3 月,全量 8 周 + 12 月;**迁移包不自动清理**;家庭导出保留 30 天且每家庭最多 3 份。

## 2. 备份目录与产物

```
backups/<yyyyMMdd_HHmmss>_<kind>_<随机>/
  meta.json              清单:版本/类型/策略ID/模块/行数/文件数/字节数/SQL 的 sha256
  RESTORE.md             该包的恢复步骤(随包生成,类型不同提示不同)
  db/policy|basic|content|full|family-data.sql.gz
  files/                 含 FILES 的包与家庭包才有
    files.manifest.jsonl 逐文件清单(路径/大小/修改时间/是否硬链接)
```

- 根目录由 `app.backup.dir` 决定,留空时取 **uploads 同级** 的 `backups/`(生产即 `/opt/ihomy/backups`),**不放进 uploads**,避免被 nginx `/files/` 直接下载。
- 备份目录若确实落在 uploads 内,快照会自动排除备份目录自身。

## 3. 运维页怎么用

运维页 →「备份与迁移」(仅 OPS):

1. 顶部卡片:备份占用(含硬链接共享的**实际磁盘占用**)、磁盘可用、策略启用数/总数、最近一次成功。
2. 「备份策略」列表:每条显示名称与已选模块、周期、清理规则、最近执行状态与时间、下次执行、启停开关;操作列可**立即备份**、编辑、删除。停用的策略只停定时,仍可手动执行。
3. 「新建策略 / 编辑策略」弹窗:勾选模块(每项标注表数或「含上传文件」)、选每天/每周/每月 + 时间(+ 星期几 / 几号)、勾「自动清理旧备份」后填天数(不勾 = 不自动清理)、开关。保存后立即重注册 cron,无需重启。
4. 「生成迁移包」是一次性手动操作(全量库 + 全量文件),不受策略影响;迁移包不参与自动清理。
5. 「执行记录」列表:策略/类型/触发(手动·定时)/状态/开始时间/耗时/体积/文件数/数据行/结果说明,可按策略、类型、状态筛选;已完成的可下载与校验,任何非执行中的任务可删除(仅删文件,记录留作审计)。

同一时刻只允许一个备份任务(含手动与定时),执行中按钮置灰、列表 5 秒轮询。

「校验」会比对 `meta.json` 的哈希、把 SQL 完整解压一遍、按清单逐文件检查存在性,返回缺失文件数——换服务器前建议对最近一份全量做一次校验。

## 4. 恢复步骤(服务器上做)

包内 `RESTORE.md` 是同一份流程的随包副本,以它为准:

```bash
# 1) 停后端
sudo systemctl stop ihomy-backend

# 2) 建空库并导入(策略包 / 全量包)
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS ihomy CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
gunzip -c db/policy.sql.gz | mysql -uroot -p ihomy

# 3) 恢复上传文件(只有含 FILES 的包才有 files/)
rsync -a files/ /opt/ihomy/uploads/

# 4) 起后端并冒烟
sudo systemctl start ihomy-backend
curl -s https://<域名>/api/public/health
```

- **只勾部分模块的策略包**恢复后不是完整实例:没勾的模块表不会出现在包里,按需再导一份补上;策略包本身不做跨包合并。
- **家庭包**保留原始 `family_id` / `user_id`,建议只恢复到**全新空实例**;目标库已有数据时先核对家庭与用户 ID 是否冲突。
- 恢复前先对当前库做一次快照:`scripts/prod-backup.sh` 会做这件事(`mysqldump` 单事务 + gzip 校验),恢复脚本 `scripts/prod-restore.sh <dump> <目标库>`。

## 5. 配置项

`application.yml` 默认值,生产可在 `external.yml` 覆盖(改完重启后端):

| 键 | 默认 | 说明 |
|----|------|------|
| `app.backup.dir` | 空(= uploads 同级 `backups/`) | 备份根目录,建议单独一块盘或 NAS 挂载点 |
| `app.backup.min-free-gb` | 1 | 开跑前要求磁盘至少剩这么多 GB(另加 256MB 余量),不够直接拒绝 |
| `app.backup.max-total-gb` | 20 | 备份目录实际占用上限,超了拒绝开新任务,需先删旧备份 |
| `app.backup.download-max-gb` | 4 | 站内 zip 下载上限,超过提示直接在服务器复制备份目录 |

备份策略本身落 `sys_backup_policy` 表(由运维页维护),不再写 `sys_parameter`;升级后旧的 `sys_parameter.name = backup.policy` 不再读取,可留作参考。

## 6. 与服务器备份脚本的关系

- **站内备份**:面向「迁移 / 误删找回 / 单家庭导出」,包是自包含的(SQL + 文件 + 清单),可以直接搬到新服务器。
- **`scripts/prod-backup.sh`**:面向「本机灾备」,只做 mysqldump + uploads 只增不删的增量同步,由 systemd timer 每天 03:00 执行,留 14 天。两者互补,不要互相替代。

## 7. 常见问题

| 现象 | 原因与处理 |
|------|-----------|
| 点立即备份提示磁盘空间不足 | 触发 `min-free-gb` 或 `max-total-gb`,先删旧任务(列表操作列)或调小策略的保留天数,再确认备份盘余量 |
| 提示「已有备份任务在执行」 | 同一时刻只跑一个任务;等列表状态不再是「执行中」,或看是否上次进程被杀(重启后端会把残留 `RUNNING` 标为失败) |
| 下载失败 / 拿到的是错误 | 包超过 `download-max-gb` 会直接报错,按提示在服务器上 `scp`/`rsync` 备份目录;业务失败时前端会显示后端返回的提示 |
| 校验报文件缺失 | 备份期间有人手工删过备份目录里的文件,或磁盘写满导致复制中断;直接重跑一份,旧包可删 |
| 备份没怎么变大 | 正常:未变化的文件是硬链接,`logicalBytes`(逻辑体积)会一直涨,实际占用看「备份占用」卡 |
| 策略到点没触发 | 看策略开关是否为启用、时间与星期几/几号是否填对、服务器时区;日志按 tid 查 `ihomy-backup` 线程的 `backup` 关键字 |
| 新建策略时某张表总漏 | 该表还没归入任何模块,补 `BackupModule` 并让 `BackupModuleCoverageTest` 通过 |
| 策略删了但历史包还在 | 预期:删策略只停定时,历史任务沿用 30 天兜底清理,想立刻释放空间就在执行记录里逐条删除 |

## 8. 新增表时要做什么

`BackupModule` 决定每个策略模块包含哪些表:

- 新表必须**显式**加进某个模块的清单(按所属数据域选);漏加会被 `BackupModuleCoverageTest` 拦住(它拿 `schema.sql` 的实际建表清单比对)。
- **永不进备份**的两类:备份任务自身(`sys_backup_job`)与一次性敏感令牌(`sys_password_reset_token`)。
- 家庭导出仍按 `BackupTableSpec` 的前缀与 `familyFilter` 规则:全局种子表(角色/权限/字典/节日/参数/开源台账等)与没有 family_id 的表不进家庭包;归属关系特殊的表(如 `sys_user_pref` 按 user_id、`sys_chat_dm_message` 按收发双方)要在 `BackupTableSpec.familyFilter` 里补一条规则,否则该表的数据不会出现在家庭导出里。
- 带文件 URL 的表要先在 `mapper/FileAccessMapper.xml` 登记游客可读范围(与「文件存储」规则一致),家庭导出才会把被引用的文件一起打进包里。

表结构改动后仍须同步 `schema.sql` + `migrations.sql`(幂等),并跑一次空库全量导入实测。
